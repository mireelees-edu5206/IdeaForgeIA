4.0 Estructura de almacenamiento
- Base de datos: espacio donde se almacena la información de la aplicación. En IdeaForge AI es la base ideaforge_dev en PostgreSQL 18, ejecutada en una computadora local.
- Tabla (equivalente a colección en MongoDB): conjunto de registros del mismo tipo relacionados entre sí, como proyectos, fuentes o hallazgos.
- Registro (equivalente a documento): fila individual de una tabla con los datos de una entidad, como un proyecto específico.
- Campo (columna): propiedad que almacena un dato específico, como title o raw_idea.
- Identificador (id): valor único que identifica cada registro. En el proyecto se usa como llave primaria de tipo uuid y se garantiza que no se repita.

Fragmento real del código que define la tabla (backend/app/modules/projects/models.py):
    class Project(UUIDPrimaryKeyMixin, TimestampMixin, Base):
        __tablename__ = "projects"
        __table_args__ = (
            CheckConstraint("btrim(title) <> ''", name="title_not_blank"),
            CheckConstraint(
                f"char_length(raw_idea) BETWEEN {RAW_IDEA_MIN_LENGTH} AND {RAW_IDEA_MAX_LENGTH}",
                name="raw_idea_length",
            ),
            Index("ix_projects_user_id_updated_at", "user_id", text("updated_at DESC")),
        )
        user_id: Mapped[uuid.UUID] = mapped_column(ForeignKey("users.id", ondelete="CASCADE"))
        title: Mapped[str] = mapped_column(String(200))
        raw_idea: Mapped[str]
        status: Mapped[ProjectStatus] = mapped_column(
            str_enum(ProjectStatus, "status"), server_default=ProjectStatus.DRAFT.value
        )

4.1 Métodos de manipulación de datos (CRUD)

A. Crear una base de datos y una tabla
Comandos SQL equivalentes (la tabla real la crea Alembic, no un CREATE TABLE manual):
CREATE DATABASE ideaforge_dev;
CREATE TABLE projects (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    user_id uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title varchar(200) NOT NULL,
    raw_idea text NOT NULL,
    status varchar(20) NOT NULL DEFAULT 'draft',
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now()
);

La tabla la crea la migración inicial de Alembic (backend/alembic/versions/20260923_a1b3ade021f1_initial_schema.py).
Comando para aplicarla: uv run alembic upgrade head

B. Insertar un registro
INSERT INTO projects (user_id, title, raw_idea)
VALUES ('[id_usuario]', 'Heladería local', 'Venta de helados artesanales en Toluca con entrega a domicilio.');

Código real que inserta un proyecto (backend/app/modules/projects/service.py):
    async def create_project(self, user: User, data: ProjectCreate) -> ProjectRead:
        """Crea un proyecto nuevo para el usuario."""
        project = Project(user_id=user.id, title=data.title, raw_idea=data.raw_idea)
        self.projects.add(project)
        await self.session.commit()
        return ProjectRead.model_validate(project)

C. Insertar varios registros
INSERT INTO projects (user_id, title, raw_idea)
VALUES
    ('[id_usuario]', 'Heladería local', 'Venta de helados artesanales en Toluca con entrega a domicilio.'),
    ('[id_usuario]', 'Taller de bicicletas', 'Reparación y venta de bicicletas usadas en la colonia centro.');

Código real para varios registros (el servicio agrega uno por uno y confirma una sola vez; SQLAlchemy los envía en lote al hacer commit):
    self.projects.add(project)   # se repite por cada proyecto
    await self.session.commit()

D. Consultar todos los registros
SELECT * FROM projects;

Código real que lista los proyectos de una persona, del más reciente al más antiguo (backend/app/modules/projects/models.py, índice ix_projects_user_id_updated_at):
    Index("ix_projects_user_id_updated_at", "user_id", text("updated_at DESC"))

E. Consultar un registro específico
SELECT * FROM projects WHERE id = '[id_proyecto]';

Código real que busca un proyecto solo si pertenece al usuario (backend/app/modules/projects/service.py, función _get_owned): un proyecto de otra persona responde 404 como si no existiera.

F. Actualizar información
UPDATE projects
SET title = '[nuevo_titulo]', updated_at = now()
WHERE id = '[id_proyecto]';

Código real: al cambiar la idea, el proyecto regresa a borrador (reglas de backend/app/modules/projects/service.py, líneas 18-23 del docstring): cambiar la idea o sus atributos lo devuelve a status = 'draft'. El campo updated_at se actualiza solo por el trigger set_updated_at.

G. Eliminar un registro
DELETE FROM projects WHERE id = '[id_proyecto]';
Nota: en el proyecto, al borrar un proyecto se eliminan sus datos dependientes mediante ON DELETE CASCADE.

Código real que borra un proyecto (backend/app/modules/projects/service.py):
    async def delete_project(self, user: User, project_id: uuid.UUID) -> None:
        """Borra el proyecto, si no hay una investigación en curso."""
        project = await self._get_owned(user, project_id)
        await self._ensure_no_active_research(project)
        await self.projects.delete(project)
        await self.session.commit()

H. Consultar mediante condiciones
SELECT id, title, status FROM projects
WHERE status = 'draft'
ORDER BY title;
Ejemplo: SELECT * FROM projects WHERE status = 'structured' ORDER BY created_at;

Código real con la misma condición (backend/app/modules/projects/models.py): el campo status solo acepta draft, structured, researching o analyzed.
    class ProjectStatus(StrEnum):
        DRAFT = "draft"
        STRUCTURED = "structured"
        RESEARCHING = "researching"
        ANALYZED = "analyzed"

4.2 Métodos o sintaxis relacionados con la seguridad y niveles de acceso al sistema de base de datos

Métodos de seguridad
Los métodos que usa el proyecto para proteger la base son: autenticación de usuarios con Supabase Auth y validación del token de acceso (JWT) en la API, control de acceso por rol en la aplicación, verificación de que cada proyecto pertenezca al usuario que hace la petición, restricciones de integridad (CHECK, UNIQUE, llaves foráneas), y hash de contraseñas con Argon2 en el perfil heredado, con los refresh tokens guardados solo como SHA-256.

Niveles de acceso en PostgreSQL
- Superusuario: tiene todos los privilegios sobre el servidor. Solo se usa para administración y no lo usa la aplicación.
- Propietario de la base: administra el esquema y las tablas de ideaforge_dev. En el proyecto es el rol ideaforge.
- Rol de aplicación: permisos mínimos para leer y escribir datos, sin poder modificar el esquema. Propuesta pendiente de implementar.
- Rol de solo lectura: permite consultar datos sin modificarlos, por ejemplo para revisión o reportes. Propuesta pendiente de implementar.

Creación de usuarios y asignación de roles
Propuesta de sintaxis, pendiente de aplicar en el proyecto:
CREATE ROLE ideaforge_app LOGIN PASSWORD '[contraseña_segura]';
GRANT CONNECT ON DATABASE ideaforge_dev TO ideaforge_app;
GRANT USAGE ON SCHEMA public TO ideaforge_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO ideaforge_app;

Para revocar un permiso:
REVOKE DELETE ON projects FROM ideaforge_app;

Código real que aplica la restricción de propiedad (backend/app/modules/projects/service.py, función _get_owned, líneas 115-121): llama a self.projects.get_owned(project_id, user.id) y, si no encuentra el proyecto del usuario, lanza ProjectNotFoundError (404).

4.3 Configuración de seguridad en PostgreSQL

Usuarios independientes para cada función: la aplicación debe conectarse con un rol propio, distinto del superusuario. Estado: propuesta; hoy la conexión usa el rol ideaforge, que no es superusuario y no tiene permiso CREATEDB.

Configuración de contraseñas robustas: las contraseñas de cuenta de los usuarios de IdeaForge AI se almacenan con hash Argon2 en el perfil heredado, y las credenciales de la base de datos deben tener al menos 12 caracteres que combinen letras, números y símbolos. Estado: parcialmente implementado.

Uso de direcciones IP autorizadas: PostgreSQL debe aceptar conexiones solo desde localhost o desde las direcciones definidas en el archivo pg_hba.conf. Estado: propuesta; hoy la base solo se usa en la computadora local.

Uso de credenciales: las credenciales de conexión se guardan en el archivo .env, fuera del repositorio, y nunca se escriben en el código. Estado: implementado.

Uso de respaldos periódicos: se planea un respaldo lógico diario con pg_dump en formato custom (-Fc), con retención de 7 a 30 días. Estado: propuesta.

Uso de registros de acceso y revisión de actividad: se propone activar el registro de conexiones en PostgreSQL (log_connections) y revisar la actividad con pg_stat_activity. Estado: propuesta. La bitácora de IA (ai_api_logs) registra llamadas a los proveedores de IA, no los accesos a la base de datos.
